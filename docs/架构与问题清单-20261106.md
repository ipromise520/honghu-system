## 一、结论摘要

| 级别 | 数量 | 关键结论 |
|---|---|---|
| P0 | 1 | **SPA 静态回退存在路径穿越，未登录即可读取服务器任意可读文件**；已实测读出 `/etc/honghu/env`（JWT 密钥，421 字节）与 `/etc/hostname`。等同于可伪造超级管理员令牌接管系统，必须最优先修复。 |
| P1 | 9 | refresh token 可当 access token 用；区县管理员可自我提权为超管；用户目录对全员开放；质检推送无管理员校验；Excel 解析阻塞事件循环；`sync_jobs` 占库 250.8MB/217MB 无用预览数据；3 个遗留 cron 持续报错；`metrics/dashboard/user-ranking` 必 500；新建用户默认弱口令 123456。 |

**整体判断**：架构清晰、单机单体、模块边界合理，日常接口响应 0.02～0.9s，属于可用状态。最大风险不在性能，而在**鉴权边界与静态文件回退**；性能上最值得做的两件事是「上传预览数据治理」与「Excel 解析移出事件循环」。

## 三、问题清单

> 路径均相对 `/vol2/Trae`；`backend/app/...` 为后端源码。行号以 2026-11-06 当前代码为准。

### P0 — 必须立即修复

#### P0-1 静态回退路径穿越，未登录可读任意文件（含 JWT 密钥）

- 位置：`backend/app/main.py:314-319`（`mobile_spa`）、`backend/app/main.py:335-338`（`spa`）
- 代码：
  ```python
  fp = os.path.join(MOBILE_DIST, full_path)
  if full_path and os.path.isfile(fp):
      return FileResponse(fp)
  ```
- 现象（已实测，未读取敏感内容，仅看状态与长度）：
  - `GET /m/../../../../etc/hostname` → `200`，返回主机名
  - `GET /..%2f..%2f..%2f..%2fetc%2fhostname` → `200`
  - `GET /m/../../../../etc/honghu/env` → `200`，**421B**（该文件含 `HONGHU_SECRET_KEY`，权限 `root:ipromise`，服务进程可读）
- 影响：攻击者无需账号即可读取 `/etc/honghu/env` 拿到 JWT 签名密钥 → 自行签发 `super_admin` 令牌 → 全系统接管；也可下载 `honghu_new.db`（278MB，含全部手机号/工单/质检数据）。属于**最高危**。
- 建议改法（低风险、可回滚）：抽一个安全路径函数，`realpath` 后校验必须位于发行目录内，并显式拒绝 `..`、绝对路径、反斜杠；两处 SPA 回退统一调用。
  ```python
  def _safe_static(base: str, rel: str):
      if not rel or rel.startswith(("/", "\\")) or ".." in rel.replace("\\", "/").split("/"):
          return None
      base_r = os.path.realpath(base)
      fp = os.path.realpath(os.path.join(base_r, rel))
      if fp == base_r or not fp.startswith(base_r + os.sep):
          return None
      return fp if os.path.isfile(fp) else None
  ```
  另外建议把 `/etc/honghu/env` 权限收紧为 `600 root:root` 并改用受限读取（systemd `LoadCredential` 或 env 文件仍由 root 读、进程用 `EnvironmentFile` 时无法避免同组读，至少改为 `640 root:ipromise` 已是现状；关键是修穿越）。

### P1 — 高风险，应尽快修复

#### P1-1 refresh token 可直接当 access token 使用

- 位置：`backend/app/deps.py:10-22`（`get_current_user`）；`backend/app/security.py:26-33`
- 现象：`get_current_user` 只验签、不校验 `payload["type"]`。实测：用 `type=refresh` 的令牌请求 `GET /api/v1/auth/me` 返回 **200**。
- 影响：refresh token 有效期 7 天且前端存在 localStorage，泄露后攻击窗口被放大；与 access 令牌同权。
- 建议改法：`if payload.get("type") != "access": raise 401`；`/auth/refresh` 增加 `is_active` 校验（当前 `auth.py:129-137` 未校验停用）。

#### P1-2 区县管理员可自我提权为超级管理员

- 位置：`backend/app/routers/users.py:162-184`（`update_user`）
- 现象：`district_admin` 可更新本区县任意用户（含自己）的 `role`/`district_id`/`password`；仅校验目标用户区县相同，未限制角色变更方向，也未校验密码强度。
- 影响：任一区县管理员可把自己改成 `super_admin`，获得全市数据与用户删除权限；属于**权限提升**。
- 建议改法：
  - `district_admin` 只允许改 `real_name/phone/team/grid/position/staff_no`，禁止改 `role`、`district_id`、`password`；
  - 角色变更与密码重置统一走 `require_super_admin` + `_validate_new_password`；
  - 禁止修改自己以外的超管账号。

#### P1-3 用户目录对任意登录用户开放，泄露全量手机号

- 位置：`backend/app/routers/users.py:18-50`（`list_users` 仅 `get_current_user`）
- 现象：装维人员调用 `/api/v1/users?page=1&page_size=20` 返回 66 人，含 `phone`、锁定状态；20 条响应 18.8KB。
- 影响：全员通讯录与手机号外泄；配合 P1-2 的越权面扩大。
- 建议改法：改为 `require_admin`（桌面端用户管理页本就仅管理员可见）；若装维端确有「找人」需求，提供只返回 `real_name/district/grid` 的精简接口并分页。

#### P1-4 质检推送/撤回未做管理员校验

- 位置：`backend/app/routers/qc.py:289`（`push`）、`backend/app/routers/qc.py:351`（`unpush`）均为 `user=Depends(get_current_user)`
- 现象：任意装维人员可批量把不合格记录推给任意人、或撤回全公司推送，并写入审计日志（伪造操作人）。
- 影响：数据完整性与责任认定被破坏。
- 建议改法：`require_admin`（区县管理员也可，保留业务需要）；若要更严可校验 `district` 范围。

#### P1-5 Excel 解析同步执行，阻塞整个事件循环

- 位置：`backend/app/utils_excel.py:4 / 92 / 134 / 191`（`async def` 内部直接 `openpyxl.load_workbook`）；调用方 `backend/app/routers/sync.py:1735`、`:1999`、`h5.py:520`、`territory.py:875`
- 现象：解析函数是 `async` 但没有 `await`，在事件循环线程里做数秒级 CPU/IO；`sync/upload-batch` 还会把全部文件字节读入内存（无大小上限）。
- 影响：上传 27k 行宽表或 5 个质检表期间，**所有用户的所有接口**（含装维端首页）都会卡住；单 worker 下等同于短时宕机。
- 建议改法：
  1. 把 `load_workbook`/`pd.read_excel` 放到 `starlette.concurrency.run_in_threadpool`（或把解析函数改成同步 `def` 由 FastAPI 线程池执行）；
  2. 上传入口加 `max_part_size`/文件大小与文件数上限（如单文件 30MB、单批 20 个）；
  3. 批量解析改为逐个 `await` + 线程池，避免一次性常驻多份 DataFrame。

#### P1-6 `sync_jobs.preview_data` 长期堆积，占数据库 90%

- 位置：`backend/app/models.py:267`、`backend/app/routers/sync.py:1991`（写入全量 JSON）、`:2069`（确认时读取）
- 现象：`sync_jobs` 表 125 行、`preview_data` 合计 **234.9MB**，其中 **113 条已确认任务占 217MB**（确认后永不再用）；未确认且超 7 天的还有 11 条（6MB）。整库 278MB 中 `sync_jobs` 占 **250.8MB**。
- 影响：备份/恢复/启动迁移变慢；WAL 与页缓存被挤占；磁盘已用 89%（剩余 22GB）。
- 建议改法（需一次短维护窗口）：
  1. 代码层：`confirm` 成功后 `job.preview_data = "[]"`；新增「清理 N 天前未确认预览」；
  2. 数据层：`UPDATE sync_jobs SET preview_data='[]' WHERE status='confirmed'`，再 `VACUUM`（预计库降到 ~40MB）；
  3. 长期：预览数据落临时文件/对象存储，或压缩 JSON（gzip）后入库。

#### P1-7 三个遗留定时任务仍跑 PostgreSQL 时代旧代码，持续报错

- 位置：`crontab`（ipromise）
  - `0 8-20/2 * * 1-5  cd /home/ipromise/honghu-deploy/backend && ./venv/bin/python cron_h5_notify.py`
  - `30 8 * * *  ... auto_sync_h5_satisfaction.py`
  - `30 6 * * *  ... recompute_metrics.py`
- 现象：`/home/ipromise/honghu-deploy/backend` 是 9 月的旧副本（无 SQLite 库、代码面向 asyncpg），日志 2.2MB 持续刷 `UndefinedFunctionError: function substr(timestamp with time zone, integer, integer) does not exist`，每 2 小时一次。
- 影响：无实际产出但持续消耗资源、淹没真正的告警；运维误判风险高；`cron_h5_notify` 的「H5 催收」能力实际已失效。
- 建议改法（需确认业务是否还需要 H5 定时提醒）：停用这 3 条 crontab；若仍需能力，改为指向 `/vol2/Trae/backend` 的新脚本（目前新版已有 `cron_sync_emails.py`，每小时 `:20` 正常运行）。

#### P1-8 `/api/v1/metrics/dashboard/user-ranking` 必定 500

- 位置：`backend/app/routers/metrics.py:1592`
- 现象：`completion_users(month, user, db)` 位置参数错位（函数签名是 `(month, district='', user, db)`），把 `user` 当 `district`、`db` 当 `user`，最终 `deps.get_role(db)` 抛 `AttributeError`。实测 `GET ...?month=2026-11&limit=100` → **500**；journal 有完整堆栈。
- 影响：该接口完全不可用（当前前端未见调用，属「隐藏坏接口」）；若看板后续接入会直接白屏。
- 建议改法：改为关键字调用 `completion_users(month=month, user=user, db=db)`；顺手补一条最小接口冒烟测试。

#### P1-9 新建用户默认口令 `123456`，且不校验强度

- 位置：`backend/app/routers/users.py:148`
- 现象：`hash_password(body.get("password", "123456"))`，创建时不调用 `_validate_new_password`。
- 影响：批量建号即产生弱口令；与 P1-2 叠加可被用来维持后门账号。
- 建议改法：创建时密码必填并复用 `_validate_new_password`；或服务端生成一次性随机口令，前端展示一次。

## 五、前端检查结论
